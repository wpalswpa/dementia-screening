# 프로젝트 2. 치매 위험 조기 스크리닝 서비스

> **이 문서를 읽는 법:** 발표 준비를 위해 처음부터 순서대로 읽으면 됩니다. "우리가 무엇을, 왜, 어떻게 했고, 그 결과가 무엇인지"를 실제 작업 순서(0~7단계)대로 풀어놨습니다. 각 단계 끝의 💬 박스는 발표에서 그대로 써도 되는 설명 문장입니다. 예상 질문별 모범 답변은 [`발표_예상질의응답.md`](발표_예상질의응답.md)에 따로 있습니다.

## 프로젝트 목표

웨어러블 라이프로그(활동·수면) 데이터로 치매 위험군의 생활 패턴을 분석하고, 사용자가 자신의 라이프로그를 입력하면 위험도를 참고용으로 확인할 수 있는 FastAPI 기반 서비스로 구현합니다. 진단이 아니라 "병원에 가봐야 할 이유가 있는지"를 짚어주는 스크리닝까지가 이 프로젝트의 역할입니다.

**개발 관점의 실질 산출물은 "누수 없이 검증된 파이프라인"입니다.** 현재 성능 수치는 174명(치매 확진 12명)이라는 데이터 한계 안의 결과이고, 파이프라인 자체는 더 큰 정식 데이터(병원·기관 보유)가 들어오면 데이터 파일만 갈아끼워 그대로 재학습·재검증할 수 있게 설계되어 있습니다. 전처리 → 피처 생성 → 무누수 교차검증 → 통계 검증(Q5·Q6) → 서비스의 각 단계가 독립 스크립트라서, 어느 단계든 데이터만 바꿔 재실행하면 됩니다.

## 30초 요약 (발표 전 마지막으로 읽을 것)

```text
데이터   : AI Hub 웨어러블 라이프로그 174명 (정상 111 / 경도인지장애 51 / 치매 12)
질문     : 병원 검사 없이 활동·수면 기록만으로 위험군(경도인지장애+치매)을 걸러낼 수 있는가?
방법     : 사람마다 "평균 + 날마다의 들쭉날쭉함(변동성)" 지표 44개 생성
          → 로지스틱 회귀로 분류, 50회 반복 교차검증으로만 성능 보고
결과     : 위험군의 절반 이상(52.7%) 탐지, AUC 0.601,
          구분 능력이 우연이 아님을 통계로 확인 (p=0.006)
핵심 발견: 활동량 "평균"보다 활동·수면 패턴의 "불규칙함"이 위험 신호
한계     : 경도인지장애 "단독" 조기 신호는 못 찾음(Q5) — 그래서 주장 범위를
          "위험군(통합) 스크리닝"으로 한정. 재현율 수치는 통계적으로 미확정(p=0.132).
서비스   : CSV 업로드 → 위험 점수 + 근거(색상 판정) + 치매안심센터 지도 안내 (FastAPI)
확장     : 업로드 자동 적재(DB) → 검진 결과 연결 → 재학습 파이프라인까지 구현 —
          "174명이라는 한계는 서비스가 돌수록 스스로 풀리는 구조"
```

# 단계별 가이드 — 우리가 한 일과 그 이유

## 0단계. 데이터 이해 — 무엇을 갖고 시작했나

**받은 것:** AI Hub "치매 고위험군 웨어러블 라이프로그" — Oura ring(반지형 웨어러블)으로 수집한 **일 단위 활동·수면 기록** + MMSE 검사 점수 + 의사가 매긴 진단 라벨. 안내 문서상 전체 규모는 300명이지만 **실제 다운로드된 것은 174명**(학습용 141 + 검증용 33)입니다.

**진단 라벨:**

| 값 | 의미 | 인원 |
|---|---|---|
| CN | Cognitive Normal, 정상 | 111명 |
| MCI | Mild Cognitive Impairment, 경도인지장애 (치매 전 단계) | 51명 |
| Dem | Dementia, 치매 | 12명 |
| CI (`diag2class`) | MCI+Dem을 합친 "위험군" — **모델이 실제로 CN과 구분하는 대상** | 63명 |

**주요 원본 컬럼 (사람×일 단위):**

| 컬럼 | 의미 |
|---|---|
| activity_steps | 하루 걸음 수 |
| activity_score | Oura가 매긴 하루 활동 점수(0~100) |
| activity_total | 하루 총 활동 시간(분) |
| activity_high / medium / low / inactive | 강도별 활동 시간(분) |
| activity_cal_total / activity_average_met | 소모 칼로리 / 평균 운동대사량 |
| activity_non_wear | **반지 미착용 시간(분)** — 길수록 그날 기록을 믿기 어려움 |
| sleep_score / sleep_efficiency | 수면 종합 점수 / 수면 효율(실제 잔 시간 비율 %) |
| sleep_total, sleep_deep / light / rem | 총 수면 시간, 단계별 수면 시간(초) |
| sleep_onset_latency / sleep_restless | 잠들기까지 걸린 시간 / 뒤척임 비율(%) |
| sleep_hr_average | 수면 중 평균 심박수 |

**MMSE란, 그리고 왜 모델에 안 넣었나:** MMSE(간이정신상태검사)는 병원에서 치매 선별에 가장 흔히 쓰는 30점 만점 인지기능 검사입니다(24점 미만이면 인지저하 의심). 우리 데이터에서도 CN 평균 27.7 → MCI 25.8 → Dem 16.6으로 뚜렷하게 낮아집니다. **그런데 진단 라벨 자체가 의사가 MMSE 등을 보고 매긴 것이라, MMSE를 입력값으로 쓰면 정답을 보고 정답을 맞히는 순환 논리가 됩니다.** 게다가 "병원 검사 없이 걸러낸다"는 서비스 취지 자체가 사라지므로, MMSE는 참고용 그래프에만 쓰고 모델 입력에서는 뺐습니다.

> 💬 **발표용 한 줄:** "저희는 병원 검사 점수는 일부러 빼고, 오직 웨어러블이 자동으로 기록하는 활동·수면 데이터만으로 위험군을 구분할 수 있는지 실험했습니다."

## 1단계. 전처리 — 믿을 수 있는 날만 남기기 (`preprocessing/01`)

**한 일:** 활동 CSV와 수면 CSV를 사람(이메일)·날짜 기준으로 병합하고, **반지 미착용이 하루 180분(3시간) 이상인 날은 통째로 제외**했습니다. 수면 기록은 자정을 넘겨 자는 경우가 많아 "잠에서 깬 날"을 그 기록의 날짜로 정했습니다(자정 교차 처리).

**왜:** 반지를 벗어둔 날의 "걸음 수 0"은 실제 활동이 아니라 결측입니다. 이런 날을 남겨두면 모델이 엉뚱한 패턴을 배웁니다.

**결과물:** `data/processed/lifelog_daily_clean.csv` — 174명, 사람당 28~118일(평균 66일)의 정제된 일 단위 기록.

> 💬 **발표용 한 줄:** "기기를 벗어둔 날의 기록은 가짜 0이기 때문에, 미착용 3시간 이상인 날은 분석에서 제외하는 것부터 시작했습니다."

## 2단계. 사람 단위 피처 만들기 — "평균"과 "들쭉날쭉함" (`preprocessing/02`)

**한 일:** 한 사람의 수십 일치 기록을 **한 줄로 요약**했습니다. 활동·수면의 18개 지표마다 두 가지를 계산합니다:

| 접미사 | 의미 |
|---|---|
| `_mean` | 관측 기간 평균 — "이 사람은 평소 얼마나 걷고 자는가" |
| `_std` | 관측 기간 표준편차 — "**날마다 얼마나 들쭉날쭉한가**(변동성)" |

추가로 `steps_cv`(걸음 수 변동계수), `bedtime_irregularity`/`wake_irregularity`(취침·기상 시각이 날마다 얼마나 흔들리는지), `day_count`(유효 일수)를 만들어 **총 44개 피처**가 됩니다.

**왜 변동성인가:** 인지기능이 떨어지면 "매일 비슷한 시간에 자고 일어나고 움직이는" 일상 루틴 유지 능력이 먼저 흔들릴 수 있다는 가설 때문입니다. 이 가설은 나중에 4단계에서 실제로 데이터로 확인됩니다.

**결과물:** `data/processed/feature_table.csv` (174명 × 44피처 + 라벨). `preprocessing/03`은 여기에 요일 차이·추세·자기상관 등 시계열 피처 6개를 더한 v2 테이블을 만드는데, 이는 Q5 재시도용입니다(5단계 참고).

> 💬 **발표용 한 줄:** "사람마다 '평소 수준'과 '날마다의 들쭉날쭉함'을 함께 계산했습니다. 뒤에서 보시겠지만, 위험군을 가른 것은 평소 수준이 아니라 들쭉날쭉함이었습니다."

## 3단계. 탐색 분석(EDA) — 데이터가 준 첫 번째 반전 (`analysis/01`)

| 지표 | CN | MCI | Dem |
|---|---|---|---|
| 일평균 걸음수 | 10,635 | **11,383** | 8,112 |
| 평균 수면효율 | 81.8% | 80.3% | 79.1% |
| MMSE 평균(참고용) | 27.7 | 25.8 | 16.6 |

**발견:** MMSE·수면효율은 예상대로 CN > MCI > Dem 순서인데, **걸음수는 MCI가 정상군보다 오히려 많습니다.** "활동량이 줄면 위험군"이라는 단순한 가설이 이 데이터에서 깨진 겁니다.

**해석:** MCI 초기에는 불안·초조로 활동량이 오히려 늘 수 있다는 임상 보고가 있으나, 이 데이터만으로 원인 확정은 불가(추정). 중요한 것은 이 반전 때문에 "평균 활동량" 대신 "패턴의 안정성"으로 눈을 돌리게 됐다는 점이고, 이게 4단계 결과와 정확히 맞아떨어집니다.

> 💬 **발표용 한 줄:** "걸음수가 많다고 안심할 수 없다는 걸 데이터가 먼저 알려줬습니다. 저희는 이 반전을 숨기지 않고, 오히려 분석의 방향을 잡는 단서로 썼습니다."

## 4단계. 핵심 모델 — 정상군 vs 위험군 스크리닝 (`model/01`)

**구조 (단순하게 유지한 것이 의도):**

```text
50회 반복 (5조각 교차검증 × 10회, 매번 동일한 절차)
  1) 학습 데이터로만 RandomForest를 돌려 44개 피처의 중요도를 잰다
  2) 상위 10개 피처를 고른다  ← 평가 데이터는 여기 어디에도 안 들어감 (누수 방지)
  3) 그 10개로 로지스틱 회귀를 학습하고, 따로 떼어둔 평가 데이터로만 성능 측정
```

**성능 (50회 반복의 평균 ± 표준편차):**

| | 정확도 | CI 재현율 | CI 정밀도 | AUC |
|---|---|---|---|---|
| 베이스라인(무조건 "정상" 예측) | 63.8% | 0% | — | 0.5 |
| RandomForest (참고, 교체 전) | 58.0% | 38.7% | 41.9% | 0.549 |
| **로지스틱 회귀 (최종)** | **60.2%** | **52.7%** | **46.0%** | **0.601** |

**지표 읽는 법 (발표에서 반드시 이 순서로 설명):**

1. **베이스라인의 함정:** 무조건 "정상"이라고 찍으면 정확도 63.8%가 나오지만 위험군을 **한 명도 못 잡습니다**(재현율 0%). 스크리닝 도구로는 무의미합니다.
2. **우리 모델의 선택:** `class_weight='balanced'` 옵션으로 "정상을 위험군으로 조금 더 잘못 보더라도, 위험군을 놓치지 않는" 쪽으로 일부러 기울였습니다. 위험군을 놓치면 병원 갈 기회를 잃지만, 정상인이 안내받으면 무료 검진 한 번으로 끝나기 때문입니다. 이 선택의 대가로 정확도는 구조적으로 낮아집니다.
3. **그래서 주 지표는 AUC:** 임계값(0.5)에 안 묶이고 "위험군일수록 점수를 높게 매기는가"만 보는 지표입니다(0.5=동전 던지기). 의료 스크리닝 문헌의 관례이기도 합니다. 우리는 0.601 — "우연보다 분명히 낫지만 강한 판별력은 아직 아닌" 정직한 위치입니다.

**모델을 로지스틱 회귀로 바꾼 경위:** 처음엔 RandomForest였는데, 같은 무누수 프로토콜에서 3종(RandomForest / 로지스틱 회귀 / HistGradientBoosting)을 비교하니 로지스틱 회귀가 **모든 지표에서** 나았습니다. 174명짜리 작은 표본에서는 복잡한 모델이 데이터의 우연한 잡음까지 외워버려서, 규제가 강한 단순한 모델이 더 안정적이라는 교과서적 패턴입니다. (딥러닝을 안 쓴 이유도 동일합니다.)

**어떤 지표가 위험 신호였나 (50번 중 상위 10개에 뽑힌 비율):**

```text
activity_low_std(100%), sleep_restless_std(96%), sleep_light_mean(82%),
activity_total_std(62%), activity_inactive_mean(60%), activity_score_std(60%),
sleep_restless_mean(54%), activity_high_mean(50%), sleep_efficiency_mean(48%),
activity_high_std(48%)
```

1~2위가 **저강도 활동의 변동성(100%)과 수면 뒤척임의 변동성(96%)** — 50번 반복 중 거의 매번 뽑혔다는 뜻이라 가장 믿을 만한 근거입니다. 2단계의 가설("루틴 유지 능력이 먼저 흔들린다")이 데이터로 확인된 지점이고, 서비스 결과 화면의 "주요 근거" 문구도 이걸 따릅니다.

> 💬 **발표용 한 줄:** "무조건 정상이라고 찍는 것보다 정확도는 3.6%p 낮지만, 그 대가로 위험군의 절반 이상을 잡아냅니다. 그리고 위험군을 가른 핵심 신호는 활동량이 아니라 '패턴의 불규칙함'이었습니다."

## 5단계. Q5 검증 — 치매를 빼도 신호가 남는가 (`model/02`, `03`, `05`)

**왜 하나:** 계획서의 검증 게이트 ②. 4단계 결과가 사실은 "이미 증상이 뚜렷한 치매 12명" 덕분일 수 있다는 우려 때문에, **치매를 완전히 빼고 정상 111명 vs 경도인지장애 51명만으로** 같은 검증을 다시 했습니다.

| | 정확도 | MCI 재현율 |
|---|---|---|
| 베이스라인(무조건 "정상") | 68.5% | 0% |
| 기존 44개 피처 | 55.3% | 22.5% |
| 시계열 피처 추가(46개) | 57.2% | 20.5% |
| 최종 분류기(로지스틱 회귀)로 재확인 | 55.3% / 54.1% | AUC 0.52~0.54 |

**결론: 신호가 유지되지 않습니다.** 피처를 바꿔 2번, 분류기를 바꿔 1번 — 총 3번 시도해 모두 같은 결론입니다. 즉 4단계의 성능은 상당 부분 치매 단계의 뚜렷한 차이에서 나오는 것이고, **"경도인지장애만 콕 집어 조기에 잡아낸다"는 주장은 이 데이터로는 할 수 없습니다.**

**이 결과를 어떻게 다뤘나 (중요 — 게이트 질문 대비):** 검증 게이트의 목적은 "서비스에서 무엇을 주장해도 되는지"를 정하는 것이었고, 정확히 그렇게 작동했습니다. 이 결과에 따라 서비스 문구에서 "경도인지장애 조기진단" 표현을 빼고, 주장 범위를 계획서 원래 목표인 **"위험군(경도인지장애+치매 통합) 스크리닝"**으로 한정했습니다. 검증이 형식이 아니라 실제로 서비스 범위를 바꾼 겁니다.

> 💬 **발표용 한 줄:** "저희 스스로 가장 아픈 질문을 먼저 던졌습니다. '치매 환자를 빼도 이 모델이 작동하는가?' 답은 '아니오'였고, 그래서 저희는 주장 범위를 정직하게 좁혔습니다."

## 6단계. Q6 검증 — 이 결과가 우연은 아닌가 (`model/04`)

**방법 (Permutation Test):** "누가 위험군인지" 라벨을 무작위로 뒤섞은 가짜 데이터에 똑같은 파이프라인을 500번 적용해서 "우연히 나올 수 있는 성능"의 분포를 만들고, 실제 성능이 그 분포를 벗어나는지 봅니다.

| | 정확도 | CI 재현율 |
|---|---|---|
| 우연 분포 평균(라벨 셔플 500회) | 51.0% | 47.7% |
| **실제 관측값** | **62.8%** | **54.7%** |
| **p-value (우연히 나올 확률)** | **0.006 ✅ 통과** | 0.132 ❌ 미통과 |

**해석:** 정상군과 위험군을 **구분하는 능력 자체는 우연이 아닙니다**(500번 중 3번 꼴로만 우연히 나올 수치). 반면 재현율은, 라벨을 섞어도 우리 모델 설정상 위험군 판정이 자주 나와서 우연 기준선 자체가 높고(47.7%), 그래서 "52.7%를 잡아낸다"는 **수치를 통계적으로 단정할 수는 없습니다.** Q6은 **부분 통과**이고, 그래서 발표·서비스 문구에서 재현율 수치를 못박지 않습니다.

> 💬 **발표용 한 줄:** "구분 능력이 진짜라는 건 통계로 증명했지만, '몇 퍼센트를 잡아낸다'는 숫자는 표본이 작아 단정하지 않습니다 — 이 구분까지가 저희가 확인한 정확한 사실입니다."

```text
③ 결과 화면       위험 점수 게이지 (0.5 이상이면 "위험군 추정")
                  판단 근거 3가지 — 정상군 평균과 가장 크게 다른 지표를 막대로 비교

                  ⚠ 한계 고지 — "진단이 아닌 참고용, 표본 174명(치매 12명)"
```

**치매안심센터 연동 (공공데이터포털 실데이터):** `service/fetch_centers.py`가 공공데이터포털 「전국치매센터표준데이터」의 공개 다운로드 엔드포인트를 호출해 **전국 317곳(치매안심센터 307·광역치매센터 9·상담전화센터 1)의 이름·주소·위경도·전화번호·프로그램 정보**를 받아 `service/data/dementia_centers.csv`로 저장합니다. 서비스의 `/centers` API는 이 데이터를 읽어 (1) 브라우저 위치 기반 — 하버사인 공식으로 직선거리 계산해 가까운 순, (2) 지역명 검색 — 두 가지 방식으로 센터를 찾아주고, 화면에는 목록과 함께 Leaflet 지도에 마커로 표시됩니다. 실시간 호출 대신 "연동 스크립트 + 로컬 캐시" 구조를 쓴 이유는 **발표 시연 중 인터넷이 끊겨도 검색이 죽지 않게** 하기 위해서입니다(지도 타일만 온라인 필요 — 오프라인이면 지도만 숨고 목록은 유지). 데이터 갱신은 `python service\fetch_centers.py` 한 번이면 됩니다.

**(선택) Oracle 적재:** `database/` 폴더에 센터 데이터를 Oracle에 적재하는 스크립트(테이블 생성 SQL → INSERT 파이썬 → 검증 쿼리)를 넣어뒀습니다. "외부 데이터 → DB 적재 → 서비스 조회" 파이프라인을 보여주는 용도이며, 시연 기본 경로는 안정성을 위해 CSV입니다. 임상(환자) 데이터는 DB에 넣지 않습니다 — 개인정보이기 때문이고, 넣을 필요도 없습니다.

**시연 시나리오 (실측 검증 완료):** 정상군 샘플 업로드 → 위험 점수 0.294, "뚜렷한 위험 신호 없음" / 위험군 샘플 업로드 → 위험 점수 0.644, "위험군 추정 + 전문기관 안내" → "내 위치에서 가까운 센터 찾기" 클릭 → 지도에 가까운 센터 5곳 표시(광주 시청 좌표 테스트: 서구 치매안심센터 1.4km, ☎ 062-350-4759). 오류 경로(컬럼 누락, 기록 14일 미만, 위치 거부, 없는 지역명)도 전부 한국어 안내로 처리됩니다.

**설계 포인트:** 서비스는 학습 코드와 같은 방식으로 지표를 계산하므로(코드에 명시), 모델이 재학습되면 `model_cn_ci.pkl`만 갱신하면 서비스도 자동으로 새 모델을 씁니다 — "데이터가 좋아지면 그대로 갈아끼운다"는 파이프라인 철학이 서비스까지 이어집니다.

## 8단계. 적재·재학습 파이프라인 — 상용화 데이터 루프 (`service/storage.py`, `model/06`)

상용 서비스라면 업로드가 일회성으로 사라지면 안 됩니다. 데이터가 쌓이고, 그 데이터로 모델이 좋아지는 루프가 있어야 합니다:

```text
① 업로드 자동 적재     사용자가 CSV를 올리면 예측과 동시에 DB(SQLite, data/service.db)에
                      익명 ID로 저장 — 일 단위 원본 기록 + 예측 결과. 적재가 실패해도
                      예측 응답은 정상 반환(적재는 예측의 부가 기능).
② 검진 결과 연결       위험군 안내를 받은 사용자가 실제 검진을 받으면, 기관이 확진 결과를
                      입력: POST /uploads/{id}/label?diagnosis=CN|MCI|Dem
                      (적재 현황 조회: GET /uploads/stats)
③ 재학습              python model\06_retrain_from_uploads.py
                      라벨 붙은 업로드만 골라 → 기존 174명과 동일한 44개 피처로 변환 →
                      기존 학습 데이터와 결합 → model/01과 같은 무누수 절차로 재평가 →
                      기존 모델 백업 후 교체. 전후 성능 비교가 reports/retrain_report.json에 남음.
④ 서비스 반영          uvicorn 재시작만 하면 새 모델 사용 (모델 파일 교체 구조 덕분)
```

**설계 원칙 (질문 대비):**
- **라벨 없는 업로드는 학습에 쓰지 않습니다.** 정답 없이 학습하면 모델이 자기 예측을 정답처럼 배우는 오염이 생깁니다. 확진 결과가 연결된 데이터만 학습에 들어갑니다 — 계획서 2단계(모니터링→모델 개선)의 정직한 구현입니다.
- **최소 신규 라벨 수(기본 10건) 미만이면 재학습을 거부**합니다. 몇 건으로는 성능이 의미 있게 바뀌지 않기 때문입니다 (`--min-new`로 조정 가능).
- DB는 설치가 필요 없는 SQLite를 기본으로 썼고(시연 어디서든 동작), Oracle 전환 시 `database/` 폴더의 센터 적재 스크립트와 같은 패턴으로 `storage.py`의 SQL만 바꾸면 됩니다.
- `data/service.db`에는 업로드된 개인 생활기록이 담기므로 git에 올리지 않습니다(.gitignore 처리).

**검증:** 업로드 2건 → 적재 확인(168개 일 단위 레코드) → 라벨 입력(CN/MCI) → 재학습 실행 → 모델 백업·교체·리포트 생성까지 전체 루프 실측 테스트 완료. (테스트에 쓴 샘플은 기존 학습 데이터와 중복이라, 테스트 후 원래 모델로 복원해 둠)

> 💬 **발표용 한 줄:** "지금 174명이라는 한계는, 서비스가 돌수록 스스로 풀리는 구조입니다 — 업로드가 쌓이고 검진 결과가 연결되면, 같은 검증 절차로 재학습해서 모델이 계속 좋아집니다."

## 코드 리뷰 (전처리 + 모델링) — 우리가 스스로 찾아 고친 것들

### 잘 짜여진 부분

- **재현 가능성**: 모든 스크립트가 입력/출력 경로를 파일 맨 위에 상수로 박아두고, 실행하면 어떤 파일이 몇 명분 나오는지 콘솔에 그대로 찍는다. 중간에 결과가 이상해지면 바로 티가 난다.
- **날짜 조인 로직**(`preprocessing/01`): `activity_day_start`가 고정값이라는 것과 수면 데이터의 자정 교차 문제를 실제 데이터로 확인하고 짠 흔적이 주석에 남아있다. 추측이 아니라 검증 후 작성.
- **테스트셋 유출 방지**(`model/02`, `model/03`): 바깥 루프(성능 평가)와 안쪽 루프(피처 개수·종류 선택)를 완전히 분리한 Nested CV가 정확히 의도대로 구현되어 있다.
- **Permutation Test**(`model/04`): p-value를 `(우연이 관측치보다 크거나 같은 횟수 + 1) / (전체 횟수 + 1)`로 계산 — 관례적으로 맞는 공식(p=0 방지).

### 수정한 문제 — `model/01`의 피처 선택 누수 (발견 → 수정 → 재검증 완료)

기존 `model/01`은 피처를 고르는 교차검증과 성능을 재는 교차검증이 **서로 다른 분할**이어서, 한 사람의 데이터가 피처 선택 때는 학습용, 성능 측정 때는 시험용으로 겹칠 수 있었다(시험 범위를 미리 살짝 본 셈). 이중 루프를 없애고 "매 반복마다 학습 데이터로만 피처를 고르고, 그 반복의 평가 데이터로만 성능을 잰다"는 원칙 하나로 다시 짰다:

| | 수정 전(누수 있음) | 수정 후(누수 없음) |
|---|---|---|
| 정확도 | 64.8% | 58.0% |
| CI 재현율 | 46.0% | 38.7% |

예상대로 숫자가 내려갔다 — 이전 64.8%는 누수로 부풀려진 수치였다. **좋아 보이는 숫자 대신 맞는 숫자를 택했다.**

### 개선한 부분 — 최종 분류기를 RandomForest에서 로지스틱 회귀로 교체

누수를 걷어낸 정직한 숫자가 너무 낮아서, 같은 무누수 프로토콜을 유지한 채 분류기 3종을 비교했다. 로지스틱 회귀가 모든 지표에서 가장 나았다(정확도 58.0→60.2%, 재현율 38.7→52.7%, AUC 0.549→0.601). 피처 중요도 산출은 해석 가능성 때문에 RandomForest 유지, 최종 판정만 로지스틱 회귀. Q6(`model/04`)와 Q5 재확인(`model/05`)도 최종 분류기와 동일 구성으로 다시 돌려 결과를 반영했다.

## 중요한 안내

- raw_data는 AI Hub 안내 문서의 전체 규모(300명)가 아니라 **실제 다운로드된 174명**(CN 111 / MCI 51 / Dem 12) 기준입니다. SNSB, 역학변수(연령·성별·학력) 파일은 포함되어 있지 않습니다.
- MMSE 점수는 모델 입력에서 제외합니다(순환 논리 방지 — 0단계 참고).
- 모델 성능은 반드시 **반복 교차검증**의 평균±표준편차로만 보고합니다. 단일 분할 숫자는 운에 좌우됩니다.
- 문제인식 시각화(발표 인트로용)와 EDA/모델링 시각화(분석 결과용)는 목적이 다릅니다. 문제인식 쪽은 청중이 배경지식이 없다고 가정하고 수치마다 쉬운 설명을 붙입니다.
